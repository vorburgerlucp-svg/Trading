# O16: Safety Alerting, Append-Only Audit & Human Reset Authorization V1

Status: design first. Base: `947a873` (O15 Portfolio Safety Envelope & Latching Kill Switch V1 merged and green).

## 1. Goal

O16 adds the governance layer around O15:

1. deterministic safety alert batches;
2. append-only audit events for safety decisions, alerts and reset governance;
3. a human, two-person kill-switch reset authorization workflow;
4. explicit recovery evidence before authorization.

O16 does **not** clear the O15 kill switch.

> Authorization is not execution.

A reset authorization is an immutable artifact that a later operational milestone may consume. O16 itself never turns a persisted `TRIPPED` O15 switch back to `ARMED`.

## 2. Existing foundations reused

O16 reuses:

- O15 `PortfolioSafetyDecision`;
- O15 `verifyPortfolioSafetyDecision`;
- O15 `evaluatePortfolioSafetyEnvelope`;
- O15 append-only `PortfolioKillSwitchStore`;
- O15 `RiskDayTracker`;
- generic `AppendOnlyLog`;
- generic `AuditLog`;
- canonical `hashOf`.

O16 does not duplicate O15 limit math.

## 4. Safety alert batch

Input:

- one verified O15 decision;
- explicit alert policy.

Output:

```ts
interface SafetyAlertBatch {
  alertBatchId: string;
  version: 'safety-alert-batch:v1';
  safetyDecisionId: string;
  safetyDecisionFingerprint: string;
  asOf: string;
  alerts: SafetyAlert[];
  batchFingerprint: string;
}
```

V1 does not deliver notifications over email/SMS/push.

It produces append-only, transport-neutral alert artifacts.

## 5. Alert policy

At minimum:

```ts
interface SafetyAlertPolicy {
  version: 'safety-alert-policy:v1';
  emitNormalState: false;
  emitCapacityBlock: true;
  emitDataHold: true;
  emitTrip: true;
  includeAllReasons: true;
}
```

V1 policy is intentionally conservative.

A `TRIPPED` decision always produces at least one critical safety alert.

## 6. Alert severity

V1:

- `NORMAL` -> no alert;
- `CAPACITY_BLOCK` -> warning;
- `DATA_HOLD` -> warning;
- `TRIPPED` -> critical.

O15 alert descriptors are preserved as source references.

O16 may group descriptors but may not downgrade an O15 `trip` descriptor below critical.

## 7. Alert determinism and dedupe

Same:

- safety decision;
- policy;

must produce the same alert batch identity.

Alert ordering is canonical by:

1. severity;
2. code;
3. reason.

No wall clock and no random alert id.

## 8. Append-only safety audit

Extend the generic AuditLog event vocabulary with:

- `SAFETY_DECISION`
- `SAFETY_ALERT_BATCH`
- `KILL_SWITCH_RESET_REQUESTED`
- `KILL_SWITCH_RESET_APPROVED`
- `KILL_SWITCH_RESET_REJECTED`
- `KILL_SWITCH_RESET_AUTHORIZED`

No event type clears the kill switch.

## 9. Safety decision audit event

A safety decision audit event binds:

- decision id;
- decision fingerprint;
- decision state;
- kill-switch trip id if present;
- O15 source fingerprints;
- O15 engine version;
- audit actor = system.

O16 verifies the O15 decision against its source request before recording.

## 10. Alert audit event

Alert batch is verified against the O15 decision before recording.

Idempotency is by deterministic alert-batch id.

A reissued batch with different content under the same id is rejected by append-only audit semantics.

## 11. Reset request

A human may request a reset only for a currently persisted O15 `TRIPPED` state.

Request:

```ts
interface KillSwitchResetRequest {
  requestId: string;
  version: 'kill-switch-reset-request:v1';
  requestedAt: string;
  requester: HumanActor;
  tripId: string;
  tripFingerprint: string;
  rationale: string;
  recoveryDecisionId: string;
  recoveryDecisionFingerprint: string;
  policyFingerprint: string;
}
```

The request references a recovery assessment generated by O16.

## 12. Recovery assessment

Because a persisted O15 switch remains `TRIPPED` by design, O16 evaluates recovery using a **hypothetical ARMED state** only for the reset-gate calculation.

The actual stored switch remains untouched.

Recovery assessment must:

- use the same current portfolio/day/policy sources as O15;
- replace only `previousKillSwitch` with a canonical synthetic ARMED state;
- be verified by `verifyPortfolioSafetyDecision`;
- result in `NORMAL`.

Therefore authorization is refused when the current portfolio is:

- `TRIPPED` on fresh hard breaches;
- `DATA_HOLD`;
- `CAPACITY_BLOCK`.

A reset is not authorized merely because the original breach disappeared.

## 13. Reset policy

```ts
interface KillSwitchResetPolicy {
  version: 'kill-switch-reset-policy:v1';
  minimumCooldownMs: number;
  authorizationTtlMs: number;
  requireDistinctApprover: true;
  requireRecoveryState: 'NORMAL';
  minimumRationaleLength: number;
}
```

All millisecond values are positive safe integers.

## 14. Cooldown

Authorization requires:

```
approval.approvedAt - killSwitch.trippedAt >= minimumCooldownMs
```

The clock is explicit input.

No wall-clock call inside pure authorization logic.

## 15. Two-person rule

Requester and approver must be different human identities.

V1 refuses:

- same actor requesting and approving;
- system/model/quant actors;
- blank actor ids;
- malformed actor ids.

This is a governance safety rule, not a UI convention.

## 16. Human approval

Approval:

```ts
interface KillSwitchResetApproval {
  approvalId: string;
  version: 'kill-switch-reset-approval:v1';
  requestId: string;
  approvedAt: string;
  approver: HumanActor;
  decision: 'APPROVE' | 'REJECT';
  rationale: string;
  requestFingerprint: string;
}
```

Approval identity is deterministic from its content.

## 17. Rejection

A rejection is append-only and terminal for that request.

A rejected request cannot later be converted to approved by rewriting the event.

A new reset attempt requires a new request id.

## 18. Authorization

Authorization exists only if:

- source O15 trip is valid and still the current persisted trip;
- reset request is valid;
- recovery assessment is NORMAL;
- cooldown elapsed;
- approval is APPROVE;
- requester != approver;
- request/approval/policy fingerprints all match;
- approval occurs after request;
- current time is not before approval;
- authorization expiry is deterministic:
  `approvedAt + authorizationTtlMs`.

Output:

```ts
interface KillSwitchResetAuthorization {
  authorizationId: string;
  version: 'kill-switch-reset-authorization:v1';
  requestId: string;
  approvalId: string;
  tripId: string;
  authorizedAt: string;
  expiresAt: string;
  requester: HumanActor;
  approver: HumanActor;
  recoveryDecisionId: string;
  recoveryDecisionFingerprint: string;
  authorizationFingerprint: string;
  applyAllowed: false;
  liveOrderAllowed: false;
  physicalPurchaseAllowed: false;
}
```

The explicit `applyAllowed: false` prevents O16 authorization from being mistaken for an operational reset command.

## 19. No reset application API

O16 must not export:

- `resetKillSwitch`
- `clearKillSwitch`
- `armKillSwitch`
- `unlatchKillSwitch`
- any API that writes ARMED state into the O15 store.

O15 `PortfolioKillSwitchStore` remains monotonic.

## 20. Authorization verification

Expose:

```ts
verifyKillSwitchResetAuthorization(inputs, authorization)
```

Verifier recomputes:

- recovery assessment;
- request identity;
- approval identity;
- cooldown;
- expiry;
- two-person rule;
- fingerprints;
- authorization identity.

It must not trust stored booleans or ids.

## 21. Append-only reset governance store

Reset request, approval/rejection and authorization artifacts are stored append-only.

The governance log must refuse:

- duplicate request id with different content;
- second terminal approval/rejection for one request;
- authorization after rejection;
- two authorizations for one request;
- approval before request;
- stale/mismatched trip id.

## 22. Audit actor identity

V1 HumanActor:

```ts
interface HumanActor {
  kind: 'human';
  id: string;
}
```

IDs are opaque identifiers, not names or email addresses.

O16 does not contain authentication; it assumes the caller passes an authenticated actor id.

This is an explicit trust boundary.

## 23. Pure core vs orchestration

Pure functions:

- build/verify alert batch;
- build/verify reset request;
- build/verify reset approval;
- authorize/verify reset authorization;
- compute recovery assessment.

Append-only orchestration:

- save safety audit events;
- save reset-governance artifacts.

No broker/network/UI action inside O16 domain logic.

## 24. PostgreSQL compatibility

Use the generic `AppendOnlyStore` ports so production wiring may use `PostgresAppendOnlyStore`.

O16 does not add a broker or external notification transport.

## 25. RED test matrix

Before implementation, tests should prove at least:

### Alerting
1. NORMAL -> no alerts
2. CAPACITY_BLOCK -> warning batch
3. DATA_HOLD -> warning batch
4. TRIPPED -> critical batch
5. O15 trip descriptor cannot be downgraded
6. same decision/policy -> same batch id
7. alert reason order does not change identity
8. tampered batch fails verification
9. changed source decision changes batch identity

### Safety audit
10. safety decision recorded append-only
11. repeated identical safety event is idempotent
12. same id/different payload is rejected
13. alert batch audit references exact decision
14. malformed/unverified decision refused before audit

### Recovery
15. persisted TRIPPED + hypothetical current NORMAL -> recovery NORMAL
16. fresh hard breach -> reset recovery refused
17. DATA_HOLD -> reset recovery refused
18. CAPACITY_BLOCK -> reset recovery refused
19. actual persisted switch remains TRIPPED after recovery calculation

### Reset request
20. request only for current persisted trip
21. malformed rationale refused
22. request identity deterministic
23. changed recovery decision changes request identity
24. changed trip changes request identity

### Approval
25. same human cannot approve own request
26. distinct human may approve
27. approval before request refused
28. REJECT produces no authorization
29. malformed rationale refused
30. changed request fingerprint refused

### Cooldown/TTL
31. one ms before cooldown -> refused
32. exactly cooldown -> allowed
33. approval time canonical UTC
34. TTL positive safe integer
35. expiresAt deterministic
36. expired authorization fails verification when evaluated at later explicit time

### Authorization
37. valid request + approval + NORMAL recovery -> authorization
38. applyAllowed always false
39. liveOrderAllowed always false
40. physicalPurchaseAllowed always false
41. tampered authorization id fails
42. tampered expiry fails
43. tampered actor fails
44. tampered recovery fingerprint fails
45. verifier recomputes from sources

### Governance log
46. duplicate terminal approval refused
47. approval after rejection refused
48. duplicate authorization refused
49. stale trip request refused
50. no reset/clear/arm/unlatch API exists

### Regression
51. O15–O9 and all existing tests remain green
52. LockedBroker behavior remains unchanged

## 26. Four-eyes review targets

Independent review should attack:

- same-person approval bypass;
- actor-id normalization/case tricks;
- timestamp/cooldown boundary tricks;
- stale trip reset;
- recovery based on stale portfolio/day data;
- DATA_HOLD incorrectly treated as recovered;
- authorization replay;
- request/approval substitution;
- TTL manipulation;
- alert severity downgrade;
- append-only terminal-state races;
- audit idempotency conflicts;
- accidental operational reset;
- any route that changes `allowLiveTrading`.

## 27. Trust boundaries

O16 does not authenticate humans.

The caller/platform must provide an authenticated human actor id.

O16 does not prove notification delivery.

O16 does not prove every intraday valuation checkpoint exists; that remains the O15 RiskDayTracker sampling contract.

O16 does not apply reset authorization.

## 28. Safety

Live Trading remains LOCKED.

Broker Orders remain LOCKED.

Physical Purchase remains LOCKED.

A reset authorization is evidence for later manual/operational handling, not permission to trade.
